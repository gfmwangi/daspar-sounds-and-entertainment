# Completion outcomes

## [x] PostgreSQL-backed catalogue, accounts, sessions, inquiries, and audit records
Use PostgreSQL through a private `DATABASE_URL`; do not treat a JSON file as the production database. Add versioned schema migrations and preserve the existing 30 catalogue products, 10 categories, descriptions/specifications, and 38 supplied photo references. Seed initial catalogue data only when the database needs initialization; do not overwrite administrator-edited products on later server starts. Product CRUD, session records, inquiries, dashboard metrics, and audit entries must be stored durably and use parameterized SQL/transactions where needed. A valid live API response containing empty product or category arrays is authoritative and must not be replaced with stale bundled catalogue data. Authenticated administrators must be able to review recent saved customer inquiries in the dashboard; unauthenticated visitors must not access inquiry records.

## [x] Secure administrator sign-in and owner-only account lifecycle
Require administrator sign-in before displaying dashboard product content or allowing product API access. Protect every administrator API endpoint server-side. Do not offer open/public account registration. Provision the first owner account only through a restricted setup or CLI path; hash passwords; keep secrets out of source control, browser code, API responses, and logs. Use an HttpOnly session cookie, secure HTTPS attributes in production, exact CORS origins, and protections against forged cross-site write requests. Provide an authenticated Account Settings screen where the owner can view the current email, change the email only after providing the current password, and change the password only after providing the current password, a matching confirmation, and a new password from 12 to 128 characters. Either change revokes active sessions and requires signing in again.

## [x] One-time first-owner setup and emergency recovery key
When no administrator account has ever been created, `/admin/setup.html` lets the business owner enter an email address, a password between 12 and 128 characters, and a matching confirmation. First-owner creation is atomic and permanently locks the public setup route after success; no public visitor can register another account or reopen setup. Generate a high-entropy emergency recovery key on first setup, show it in a copyable warning card, and store only a one-way verifier plus an encrypted value needed for the authenticated owner to view/copy it later. The login page shows a setup link only while server status confirms setup is incomplete. Forgot-password recovery lets the owner submit their email, emergency key, and a new password with confirmation; it must be rate-limited, generic on failure, revoke every active session on success, and rotate the recovery key, displaying the replacement once. Account Settings lets an authenticated owner view/copy or rotate the current key only after verifying the current password. Retain the private developer CLI password reset if the owner loses both password and key; do not add an unlock-setup option that recreates public registration.

## [x] Encrypted database backup and restore tooling
Provide a private command that uses `pg_dump` to export the configured PostgreSQL database, encrypts each backup with authenticated encryption using a separately configured 32-byte backup key, writes files with owner-only permissions outside tracked source paths, and prunes only encrypted backups older than the configured retention period. Provide a restore command that refuses to run without an explicit destructive confirmation, verifies the backup authentication tag and key identifier before passing a decrypted temporary dump to `pg_restore`, removes temporary plaintext on success or failure, and never logs database URLs, passwords, or encryption keys. Document that a local backup command does not create an automatic off-site schedule, managed point-in-time recovery, or a verified production restore; these require the chosen host/provider.
